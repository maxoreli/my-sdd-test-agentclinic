# Requirements: Database (Roadmap Phase 2)

## Scope

- Connect the app to a local SQLite database using Drizzle ORM on top of `better-sqlite3`.
- A Drizzle schema with one table, `agents`, and a migration generated by `drizzle-kit` and committed to the repo.
- A seed script that inserts a few playful agents and can be run more than once without creating duplicates.
- npm scripts to generate migrations, apply them, and seed: `db:generate`, `db:migrate`, `db:seed`.
- A server-side data access module for agents (count and list), used by the home page.
- The home page shows the seeded agents as a short "waiting room" line (for example, "3 agents are in the waiting room") with their names. It is server-rendered and stays responsive.
- A friendly fallback message on the home page when the database is missing or not migrated, instead of an error page.
- Adopt PicoCSS as the app's CSS framework: load it globally, style the home page and shared layout with Pico's semantic HTML defaults, and cut `layout.css` down to small overrides.
- Vitest tests for the client factory, migrations, seed, data access, and home page, all running against an in-memory database.

## Out of scope

- Any other tables: ailments, therapies, and appointments wait for Phases 5–7.
- Adding, editing, or deleting agents, and the `/api/agents` route (Phase 4).
- Navigation, the dashboard shell, and links to agent pages (Phase 3).
- Changing `GET /api/health`; it still returns `{ "status": "ok" }` without touching the database.
- Hosted or remote databases, connection pooling, and backups.
- Custom Pico themes, a colour palette, or a full visual design pass (Phase 9). Tailwind or any second CSS framework.

## Decisions

- **ORM and driver:** Drizzle ORM (`drizzle-orm`) with `better-sqlite3`; `drizzle-kit` as a dev dependency for generating migrations. This gives typed queries and committed SQL migrations on a popular stack (Mary's reliability goal).
- **Schema location:** `src/db/schema.ts`. Migrations are generated into `drizzle/` at the project root and committed.
- **`agents` table:** `id` (integer primary key, autoincrement), `name` (text, not null, unique), `model` (text, not null), `created_at` (integer timestamp, not null, defaults to now).
- **Database file:** `data/agentclinic.db` by default, overridable with the `DATABASE_URL` environment variable. `data/` is gitignored, apart from a `.gitkeep`.
- **Client:** `src/db/client.ts` exports `createDb(path)` (used by tests and scripts) and a lazily created shared `db` for the app. Only server code imports it.
- **Migrations and seeding are explicit:** you run `npm run db:migrate` and `npm run db:seed`; the app does not migrate on startup. The seed uses the `name` unique constraint (insert, ignoring conflicts), so running it again is safe.
- **Home page rendering:** the home page is dynamic (`export const dynamic = "force-dynamic"`), so `npm run build` does not need a database file.
- **Data access:** `src/db/agents.ts` exports functions that take a `db` argument (for example `countAgents(db)`, `listAgents(db)`), so tests can pass an in-memory database.
- **Tests:** each test builds a fresh `:memory:` database, runs the real migrations from `drizzle/`, and seeds it. The home page test mocks `@/db/client` to supply that database.
- **CSS framework:** PicoCSS v2, from the npm package `@picocss/pico`. Import the stylesheet `@picocss/pico/css/pico.min.css` once, in `src/app/layout.tsx`, before `layout.css`. Pico was chosen because it is lightweight, classless, mobile-first and responsive by default, and it gives a polished look (Steve's goal) without a build plugin.
- **Using Pico:** rely on semantic elements (`header`, `main`, `footer`, `article`, `ul`) and Pico's `container` class, not custom class names. Any customisation goes through Pico's CSS variables (`--pico-*`) in `layout.css`, never by overriding Pico's own selectors. Pico's automatic light and dark colour schemes are kept.
- **Responsive rules still apply:** Pico's defaults must still meet the Web UI requirements in `specs/tech-stack.md`: body text at least 16px, tap targets at least 44×44px, and no horizontal scrolling at 360px, 768px or 1280px.
- **Copy:** seeded agent names and the waiting-room line are playful and warm, per `specs/mission.md`, for example "Claude-ish (overcontexted)" or "GPT-Gary (prompt fatigue)".

## Context

- Mission: AgentClinic tracks agents, ailments, therapies, and appointments. `agents` is the core entity, so seeding it now gives Phase 4 a real table to build on instead of a throwaway one.
- Audience: course students and conference demo developers need a fresh clone to work with `npm install && npm run db:migrate && npm run db:seed && npm run dev`. There is no database server to install.
- Tech stack: SQLite as a single local file, server-side TypeScript, Vitest, and mobile-first responsive UI. See `specs/tech-stack.md`.
- Phase 1 kept the home page free of data. This phase deliberately adds one server-rendered data line to prove the full stack, from the database to the rendered HTML. It still has no navigation or links.
- Phase 1 used plain CSS. This phase replaces it with PicoCSS, so Phase 3 (dashboard shell) and Phase 9 (polish) build on a shared baseline. `specs/tech-stack.md` records Pico as the styling choice, along with its usage rules.
